# Tarea 3.4: cancelaciones tardías y suspensión automática de 30 días

- **Rama base:** `pivote/b2b-sin-pagos`. Crea `pivote/3.4-suspension-automatica` y abre un PR contra la rama base.
- **Contexto:** lee `docs/REGLAS_DE_NEGOCIO_Y_TARIFAS.md` §3.
- **Servicios:** `services/auth-service/` y `services/trip-service/`.

## Regla
Al registrarse una cancelación tardía (`trip_cancellations.had_penalty = true`):
- si el usuario acumula **3 o más en los últimos 30 días**, queda **suspendido 30 días**;
- la suspensión **se levanta sola** al vencer el plazo;
- un administrador puede levantarla antes con el endpoint que ya existe (`PATCH /admin/users/{id}/suspension`).

## Diseño (decidido, no cambiar)
- **trip-service** detecta el umbral, porque es quien tiene `trip_cancellations`, y le pide la suspensión a **auth-service** por un endpoint interno protegido con `jwt.service`. Usa el mismo patrón de token de servicio que `RouteMatchingClient` (`JwtVerifier::issueServiceToken('trip-service')`).
- **auth-service** guarda la fecha de fin en `users.suspended_until` y pone la llave de Redis **con TTL**. Los demás servicios, que solo miran Redis, quedan liberados solos cuando el TTL expira.
- **El levantamiento automático es perezoso, sin scheduler:**
  - Si `is_active = false` y `suspended_until` no es null y ya pasó, auth-service reactiva al usuario la próxima vez que pasa por `JwtAuthenticate` o por `login`.
  - Se registra en la bitácora como `auto_reactivated`.
  - **Ojo:** `deleteAccount` también pone `is_active = false`, pero con `suspended_until` null. Esas cuentas **nunca** se reactivan.
- **La suspensión manual del administrador** no tiene fecha (`suspended_until = null`) y sigue igual que hoy.

     Retorna `true` si reactivó.

## Tests
**auth-service** (Pest, como los existentes):
- el endpoint interno sin token de servicio responde 401 o 403;
- con token de servicio suspende, guarda `suspended_until` y registra en la bitácora con admin null;
- es idempotente: una segunda llamada no duplica la bitácora;
- no suspende a un administrador;
- con `suspended_until` vencido, un request autenticado reactiva al usuario y registra `auto_reactivated`; usa `Carbon::setTestNow` o `travel`;
- una cuenta borrada (`is_active = false` sin fecha) **no** se reactiva;
- el login de un usuario suspendido con fecha responde con el mensaje y la fecha;
- la reactivación manual del administrador limpia `suspended_until`.

**trip-service** (respeta el framework que ya usa el servicio; revisa `tests/Pest.php` antes de elegir):
- la 3.ª cancelación tardía en 30 días llama a auth (`Http::fake` + `Http::assertSent`) y responde `suspended: true`;
- 2 cancelaciones tardías no llaman a auth;
- las cancelaciones de hace más de 30 días no cuentan;
- una cancelación no tardía no evalúa la policy;
- si auth falla, la cancelación igual responde 200 con `suspended: false`.
